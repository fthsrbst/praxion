## 0. Research digest

Fetch limits: several pages timed out or returned 429 (Baritone docs, mineflayer-builder, the Mindcraft
README). What follows is only what a source I could read said. Everything else is marked "unknown".

| System | What it does for building | What I could verify | Lesson |
|---|---|---|---|
| Voyager ([arXiv 2305.16291](https://arxiv.org/abs/2305.16291)) | LLM writes executable JS skills, iterates on env feedback, execution errors and self-verification | Abstract has no building result; it measures items, distance, tech tree | The write / run / feedback / repair loop is what Praxion already copies. Voyager is not evidence that LLMs build well. |
| Plan4MC ([arXiv 2303.16563](https://arxiv.org/abs/2303.16563)) | Skill RL plus a skill graph; the LLM builds the graph once, humans check it | No structure building | Planning over a checked skill graph beats free LLM planning. Same direction as our admission gate. |
| APT ([arXiv 2411.17255](https://arxiv.org/abs/2411.17255)) | LLM chain-of-thought makes "architectural layouts and blueprints", memory and reflection modules correct errors | Abstract only: memory module helped in an A/B test; "scaffolding behavior" emerged. The blueprint schema is unknown to me (full paper not read). | Reflection after a failed build helps; the LLM improvises scaffolding when given the chance. We make scaffolding explicit code instead. |
| Builder dialog benchmark ([arXiv 2407.12734](https://arxiv.org/abs/2407.12734)) | Text-only builder task, zero/few-shot/CoT | Without chain-of-thought the LLM often neglects to compute one of the axes | Axis and orientation errors are the main LLM failure. Use a format where each axis is labelled and code does the arithmetic. |
| Mindcraft / MineCollab ([arXiv 2504.17950](https://arxiv.org/abs/2504.17950), via [summary](https://www.emergentmind.com/papers/2504.17950)) | Construction tasks from procedurally generated blueprints, scored by edit distance to the blueprint | Agents undo their own progress on long tasks; a bot's foundation was destroyed by teammates | Score a build by diff against the blueprint, and never let other skills dig the structure. Mindcraft's own build command internals: unknown (page timed out). |
| MineBench ([repo summary](https://www.sourcepulse.org/projects/31138598)) | Models generate voxel builds from text, ranked head-to-head | Ranking only; I could not read its format. The "VoxelCodeBench" claim in a news item is unverified. | Pairwise comparison is a way to measure beauty (§7). |
| GDMC ([arXiv 1803.09853](https://arxiv.org/abs/1803.09853), [wiki](https://en.wikipedia.org/wiki/Generative_Design_in_Minecraft)) | Settlement generators judged on adaptability, functionality, narrative, aesthetics | Organizers say generators often flatten big areas and ignore the map; entries are asked to make the map's influence visible. A 2022 winner used a terrain analysis phase; AgentCraft grows settlements bottom-up. | Variety and site-fit come from analysing the site first (heights, slope, water, materials) and letting those facts choose the design. Procedural code, not an LLM, did the placing in every entry I saw. |
| Baritone builder ([DeepWiki summary](https://deepwiki.com/cabaletta/baritone/5.1-builder-process)) | Schematic to world diff; `buildInLayers` builds one horizontal slice at a time (default off); `buildSubstitutes`; `allowPlace` / `allowBreak` | Only these settings. Exact scaffolding and ordering internals: unknown. A user report shows a schematic that includes ground blocks makes the bot dig the floor. | Build as a diff of world vs. blueprint (resumable by construction). Blueprint cells must be able to say "do not care / keep what is there". Layer order is a setting worth copying. |
| mineflayer-builder, litematica formats | Not read (timeouts). | unknown | Not needed: our blueprint is our own small format (§2); import of `.litematic` is a later option. |

Conclusion that drives the design: nobody I could read has LLMs producing site-fitted, validated builds
reliably end to end. The robust parts in the literature are (a) a diff-based executor, (b) site analysis
before design, (c) feedback and reflection after failure. The LLM's weakness is 3D arithmetic, so code does
all arithmetic and the LLM writes only a labelled, low-arithmetic description.

## 1. Persona [proposed]

A small typed profile, written once per world, edited rarely. Not a chat character: a set of biases that
change choices.

```
persona.toml            (local/persona/<world>.toml, per installation like skills)
  name:        "Odun"
  temperament: cautious | bold | tidy | wanderer            # enum, drives risk and goal choice
  taste:       { style: rustic | stone_fort | cottage | cave_burrow | tower,
                 palette: [oak_planks, cobblestone, spruce_log],  # preferred materials, ordered
                 symmetry: low | medium | high,
                 ornament: 0..3 }                          # windows, trim, lanterns, a garden
  values:      { safety: 0..3, beauty: 0..3, speed: 0..3, hoarding: 0..3 }
  fears:       [creeper, lava]                             # raises margins around these hazards
  history:     [ {build: "shelter #1", day: 1, note: "cobble box, ugly"} ]  # last N builds, written by code
```

Examples:
- Odun: tidy, taste rustic, oak + cobble, symmetry high, values safety 3 beauty 2. Builds a symmetric
  oak-and-cobble cottage with a torch at the door.
- Kor: bold, cave_burrow, speed 3 beauty 0. Digs into a hillside and seals the entrance.

Who reads it:
- Goal proposer (`brain/`): values and temperament weight the goal ranking (high safety: build shelter
  before dusk; hoarding: chest first; bold: hunt earlier). One prompt block, no new model.
- Designer (the LLM in §2): taste, palette, fears and the last 3 `history` entries go in the prompt, with
  "do not repeat the silhouette of these".
- Code: `values.speed` caps the design size (§4); `fears` add checks.

Variety without randomness for its own sake: the design differs because inputs differ. Site facts (§3),
inventory, time of day, `history` (an explicit anti-repeat rule) and the mood fields all change the prompt.
A fixed persona on a fixed site and inventory should produce a similar design; that is a feature
(a character with a style), and it is testable (§7, measurement 4). `history` is the only memory, so
variety across builds is traceable. Alternative: sample a random "seed style" per build; rejected because
it gives variety that cannot be explained or reproduced.

Open: who edits the persona, the user at setup or the bot over time (taste drift)? [open, §8]

## 2. Blueprint format [proposed: layered slices with a palette]

Compared:

| Format | LLM reliability | Code validation | Notes |
|---|---|---|---|
| Block list `[(x,y,z,block)]` | Poor: 70 to 200 triples, easy to drop or duplicate a cell, axis slips (the Builder-dialog benchmark finding) | Easy | Good as the compiled output, bad as what the LLM writes. |
| Layered ASCII slices + palette | Good: the LLM sees the shape row by row, the grid does the arithmetic, gaps are visible | Easy: parse to a dense array, check every layer has equal dimensions | Weak for big, curved or repeated structure. Fine up to about 12x12x8. |
| Small procedural program / DSL (`box`, `fill`, `hollow`, loops) | Good for large regular structure, bad for irregular detail; can loop forever or go out of bounds | Needs an interpreter and a budget; more attack surface | Matches the Voyager and GDMC style (code generates). Heavier: a new language beside the `.skill` DSL. |

Recommendation: layered slices with a palette as the one format the LLM writes (structure for small
builds). Code compiles it to a dense `Blueprint { size, cells[y][z][x] }` and then to a block list. A tiny
macro set can be added later if sizes grow: `repeat`, `mirror x` (cheap symmetry, which matches the persona
`symmetry` field). Alternative: LLM writes Python that fills a voxel array in a sandbox; rejected for now
(code execution risk, and the admission story for learned skills already costs enough).

Rules of the format:
- Origin: the lowest layer `y0` is the feet level; the floor under it is the ground and is not part of the
  blueprint. `x` runs west to east, `z` north to south, rows are `z`, columns are `x`. The header says so
  and the prompt repeats it, which removes the axis ambiguity.
- Palette maps one character to a block id or a role: `.` air that must stay air (interior), `_` do not
  care (keep what is there; this is the Baritone floor-digging fix), `e` entry (opening, sealed from inside
  as the last step), letters are blocks.
- Roles over block names where possible: `W` = "wall material", resolved from the persona palette and the
  inventory, so a blueprint is reusable when stone is short.
- Max size 13 x 13 x 9 in v0.

Exact example, small shelter (5 x 5, walls 3 high, roof at y3, one 2-high entry in the south wall, two
windows, one torch). Block count: 69 `#`, 2 `G`, 1 torch.

```
blueprint v1
size: 5 5 4            # x z y
axes: x west->east, z north->south, y up; layer y0 = feet level
palette:
  '#': cobblestone     # role: wall
  'G': glass_pane
  'T': torch           # needs a solid floor or wall to hang on
  '.': air             # must stay free
  'e': entry           # 2-high opening, sealed from inside last
  '_': keep            # do not touch

layer y0:        layer y1:        layer y2:        layer y3:
#####            #####            #####            #####
#..T#            #...#            #...#            #####
#...#            G...G            #...#            #####
#...#            #...#            #...#            #####
##e##            ##e##            #####            #####
```

The torch sits on the floor in the corner inside; the roof is solid, so no spawns inside. The shelter works
with 69 cobblestone, which is about a stack and a bit, early-game realistic. A designer that finds only
oak will rewrite `#` to `oak_planks`; code checks the new total against inventory (§4). A variant for the
Kor persona is a burrow: the same format with `_` around a hillside and no roof layer (the hill is the roof).

Error recovery for LLM output [proposed]: parse failure or a failed validation goes back to the LLM as a
typed error plus the offending layer (at most 2 repairs, same loop shape as skill admission §6.3), then
falls back to a built-in minimal box (the brain-silence fallback of the Demo-3 decision, §5.4). The
fallback is a safety net, not a template the designer copies.

## 3. Site analysis [proposed]

Code builds a compact `SiteReport` (about 1.5 KB of text) from existing perception (`blocks_in`, known
map) around a candidate anchor. The designer does not see raw blocks.

```
site (anchor 112,64,-38)   candidate footprint 9x9 around the anchor
heights (ground y relative to anchor, x west->east, z north->south):
   0  0  0  1  1  1  2  2  3
   0  0  0  0  1  1  2  2  3
   ...                                   # 9 rows; '~' water, '!' lava, '?' unknown
surface: grass 61 of 81, sand 8, water 12
slope: max step 1 in the 5x5 centre; 3 on the east edge
trees: oak at (+4,0,-3) (6 logs), hill to the east (stone visible at +3)
inventory: cobblestone 74, oak_planks 12, torch 4, glass 0
light now: day, 6200 ticks to dusk; sky light 15 at the anchor
hazards in 16 blocks: water 2 cells west, no lava seen, 1 cave mouth at (+9,-2,+5)
unknown ratio in footprint: 4%
```

Source mapping (all from existing perception, no new sensor): heights from the column scans the planner
already does for `explore` and `dig_down`; materials from `count_item` / inventory; hazards from
`BlockFilter` queries for fluids; time of day from the observation stream; unknown cells from the known map.
Anchor choice is code, not LLM: score nearby candidate anchors by flatness, distance to trees and stone,
and low unknown ratio. This matches the GDMC lesson that terrain analysis precedes design and that
flattening everything is the failure mode, so the designer may ask for `_` and cut-and-fill, and code
limits terrain edits (§4: at most N blocks removed or added to level).

## 4. Validation in code [proposed]

All pure functions of `Blueprint + SiteReport + Inventory`, run before any block is placed. Each failure is
a typed kind returned to the designer (and later to the repair loop). Unit-testable without a world.

| Check | Rule | Failure kind |
|---|---|---|
| Format | all layers same size, palette complete, only known blocks, size <= bound | `bad_format` |
| Size bounds | volume <= 13x13x9, block count <= `values.speed` budget (default 150), build time estimate <= budget | `too_big` |
| Support / gravity | every solid cell is face-adjacent (6-neighbour) to another solid cell or the ground, in some placement order (BFS from the ground); sand and gravel need a block below; torches need a solid face; no floating cell | `unsupported` |
| Materials | block count per kind vs inventory plus minable-in-sight; shortfall -> substitution via roles, else a "gather first" plan (goal, not failure) | `short_materials{block, need, have}` |
| Site fit | footprint cells at or below ground; terrain edit <= 20 blocks; no water or lava cell inside the footprint; footprint unknown ratio <= 10% | `site_conflict` |
| Shelter enclosure | flood-fill from an interior air cell through air; it must not reach the outside or the sky; the only boundary openings are `e` cells, which count as sealed because the plan seals them last | `not_enclosed` |
| Shelter spawn safety | mobs spawn at block light <= 0 in current Java rules (stated from memory, to be confirmed against the wiki RAG [open]); every interior floor cell gets light >= 1 from a torch (propagated light, 14 at the torch, minus 1 per step) or has a solid roof directly above and a torch within light range; interior height >= 2 | `dark_cell` |
| Reach / placement feasibility | a placement order exists (§5) in which every cell is placeable from a standing cell the body can reach (within about 4.5 blocks, with scaffolding from §5 if a cell is above 4 high) | `unreachable` |
| Entry | the `e` cells are reachable from outside, and after sealing from inside the body is inside; a way to leave exists (dig out), so the plan cannot trap the bot permanently | `no_exit` |
| Hazards | no placement that traps the body in lava/water; fears from persona raise margins | `hazard` |

Light rule is the one fact here I state from memory; the check should read a data file generated from the
game data, not a constant in code. Alternative: skip light checks and always put 2 torches; rejected
because it is not a validation and a window or cave can break it.

## 5. The `build` primitive [proposed]

A discrete primitive `build(blueprint_id)` in the primitives crate. One primitive, many `place` calls
inside it, in the same relation `dig_down` has to `dig` (the pattern in `dig_down.rs`: a loop of
cell-wise sub-actions, one receipt each).

```
Blueprint ──► diff vs world ──► ordered cell list ──► per cell: stand, place (reuse Place), receipt
                    ▲                                         │
                    └───────── re-diff after any interruption ◄┘
```

Order, support-first:
1. Diff: the target cells whose world state differs (cells already right are done; `_` cells ignored).
   Resuming is therefore free: the state is the world, not a counter (Baritone's approach as far as the
   summary I read shows; the code internals are unknown).
2. Sort by layer (y ascending, Baritone's `buildInLayers` idea), inside a layer by distance along a path
   that circles the footprint so the body walks the perimeter. A cell is eligible only when it has a
   support face already present (§4 support check ordering).
3. The body stands inside the footprint on the floor when it can reach all cells of the layer, outside
   when working on the outside faces; stand-cell choice is a planner query (`move_to` reuse).
4. The roof is placed from the inside via scaffolding or from above (pillaring the ceiling cells is what
   a person does).

Scaffolding: when a needed cell is above reach (y >= 4 above the standing floor) or no support face exists
yet, `build` places a scaffold block (cheapest block in inventory, tagged in a body-side set `scaffold`)
next to the target, stands on it, places, and removes scaffold in reverse order at the end, recovering the
blocks. This is explicit code. APT reports the LLM improvising scaffolding as an emergent behaviour; that
is a signal that scaffolding is needed, not a reason to leave it to the LLM. Alternative: no scaffolds,
shelters only up to reach height; rejected because beauty (towers, roofs) needs height, but v0 can start
with it (size bound y<=4, §7 step 3) and add scaffolds in step 5.

Reuse of `place` (`place.rs`): `Place` already chooses a support face, aims precisely, handles a plant in
the way (clear clicks), a body overlapping the target (re-plan), cells that swallow clicks (three
failures bans a cell for this body). `build` needs one change: `Place` today picks the nearest support
face for an air cell in its own search (`place_target`); `build` knows the exact target cell, so `Place`
gets an optional `want: Option<BlockPos>` that restricts candidates to supports of that one cell. That is
a small, reviewable change and keeps one placement implementation. The note in `place.rs` that the body
overlap check assumes a full cube becomes wrong for doors, slabs, torches and glass panes: those
need a real collision shape [open: does the game data in `praxion-gamedata` expose shapes?].

Receipts: one `place` receipt per block (existing, level 2: block state changes), `build` itself reports a
summary receipt `{placed, already_right, skipped, failed: [kinds]}`. The summary is level 3 equivalent
(a recount of the diff at the end must be 0 or the failure is typed). Typed failures: `no_item`,
`no_place` (from `Place`), `unreachable`, `scaffold_stuck`, `interrupted`, `diff_nonzero{n}`.

Interruption: a reflex (danger, mob) pre-empts; the arbiter marks `build` `preempted`. On resume the same
call re-diffs the world and continues. The brain keeps `blueprint_id` and the anchor in its goal state, not
in the body.

Bounds: at most 150 placements and 8000 ticks per call (the same style of cap as `dig_down`, 40 blocks per
call); beyond that it returns `budget` with progress and the brain re-issues.

Closing the shelter: the last step places the `e` cells from inside; this is the only step that needs the
body to stand in the footprint. Torch cells are placed after the roof.

## 6. Hunt and combat [proposed]

`hunt(mob)` as a core skill (rule-list `.skill`, in `body/skills/`), built from primitives plus reflexes.
It is a core skill, not a learned one, because it is dangerous to practice on the real world and its
behaviour needs a defined timing contract.

```
hunt(mob):
  if health low            -> retreat
  if mob in sight, near    -> fight
  if mob known             -> approach
  else                     -> find(mob)  (explore toward the habitat) ; give up after N ticks
```

Primitives and reflexes it needs (check which exist before writing any: unknown for combat):

| Need | What | Where |
|---|---|---|
| approach | `move_to` toward an entity position, re-planned every few ticks since the target moves | new thin variant `move_to_entity`, or `move_to` fed a moving goal [open] |
| attack | `attack(entity)` primitive: look at the entity, click Attack when the cooldown is ready (sword full-swing about 0.6 s in the current Java rules, stated from memory, from game data), crit by falling is optional | new primitive, receipt = entity health drop or death (level 3) |
| tactics | strafe / back off after a hit, sprint-hit knockback; fight at a doorway; creepers: hit and step back, never melee at fuse | reflexes in the arbiter, per-mob data tables |
| retreat | flee along known safe path, block behind with `place`, eat, resume | skill + reflex on health threshold |
| gear | sword/shield/armor equipped before `hunt` | the existing craft goals (`get_sword`) as preconditions |
| loot | pick up drops | existing `pickup` |

Mob habitat and spawn knowledge: the wiki RAG is decided for later. Until then, a small hand-written data
table (`mob -> biomes, light/time, drop, danger`) for the 6 target mobs (zombie, skeleton, spider, creeper,
cow, pig). Wiki RAG replaces it later; the brain asks the RAG for "where does X spawn" and hands the body a
search plan. Farms are blueprints (§2) whose mechanics (spawn platform, kill chute) come from RAG text
and are checked by the validation layer plus a live test; a farm is the last item of Demo-3.

Safety: `hunt` in the practice room runs on a held-out seed with a hostile-spawn-enabled difficulty;
failure kinds `died`, `lost_target`, `no_weapon`, `timeout`, `fled`. A death is a body failure, not a skill
failure, for the admission accounting.

## 7. Build order and measurements

Each step stands on the previous one and is verifiable alone. Tests: unit (Rust or Python, no world),
live harness (headless body, seeds 101/202/303 as existing tests).

| # | Step | Tests |
|---|---|---|
| 1 | `Blueprint` parser + palette + compile to cells (Rust, `rules` or new `blueprint` crate; decision for the user) | unit: the example above parses, wrong-sized layers fail, `_` and roles |
| 2 | Validators (§4) as pure functions | unit: floating cell, open wall, dark cell, short materials each give the typed failure; the example passes |
| 3 | `Place` takes `want: Option<BlockPos>`; `build` v0: no scaffolds, y<=4, diff/resume, summary receipt | live: build the example on flat ground, seed 101; interrupt (kill the call) and resume; `diff_nonzero == 0` |
| 4 | Site report (§3) from perception | unit on a fixed world; live: report on 3 seeds looks sane |
| 5 | Scaffolds and removal; sizes up to 9 high | live: a 7-high tower and a pitched roof; scaffold blocks recovered |
| 6 | Brain: persona file, designer prompt, repair loop, fallback box; goal proposer reads persona | unit with a fake LLM; live: 3 personas, same site, different designs; $ ledger |
| 7 | `attack`, `move_to_entity`, retreat reflex, `hunt` skill, mob table | live: zombie on flat ground at day, kill with sword; health never below N |
| 8 | Hunt for an item (a mob far away: explore -> hunt -> pickup) | live on 3 seeds |
| 9 | Farm blueprints from RAG text | later, after the wiki RAG |

Five measurements, recorded in `docs/sessions/` after each step:
1. Design validity: % of LLM blueprints that pass §4 on first try, and after 2 repairs, per model (luna,
   terra), on 10 sites. Target to be set from the first run: unknown.
2. Build fidelity: after `build`, `diff_nonzero`, placed blocks per 100 ticks, % of runs with all cells right;
   resume correctness after a forced interruption (must be 100%).
3. Shelter function: spawn check in game, a night with the shelter closed: zero mob contact inside; cost in
   ticks and blocks.
4. Variety and site fit: for 3 personas and 3 sites, pairwise distinct silhouettes (normalized edit distance
   between blueprints), and the same persona on the same site gives close designs; judged by a Claude
   subagent plus the user, MineBench-style pairwise preference for beauty.
5. Hunt: kill rate and health lost per kill for 5 mobs across 3 seeds; deaths per 100 minutes; time to find
   a named mob from a cold start.

## 8. Risks and open questions

Risks:
- LLM design cost: a 2-repair loop can cost several designer calls per build; the cost ledger of Demo-2
  must cover it [measurement 1 gives the number].
- `place` is tuned for one block at a time with ~40-tick receipts; 70 blocks is long but acceptable; a
  slow build near dusk is a risk, so the first-night fallback box must be fast (a minimum design).
- Collision shapes for non-cube blocks; light propagation and spawn rules must come from data, not memory.
- Combat is a new class of body failures (death, respawn). The arbiter already handles respawn
  (`place.rs` mentions it).
- Beauty is subjective; measurement 4 is a proxy.

Open questions for the user:
1. Blueprint format: layered slices + palette as the writer format, no DSL at first. OK?
2. Persona: who edits it, you at setup or the bot over time? Keep `history`-based anti-repeat?
3. Where do blueprints live: a Rust `blueprint` crate (validators in Rust, near the body) or Python in
   `brain/`? I lean Rust for the validators that need game data (light, collision) and Python for the prompt.
4. Scaffolding in v0 or later (step 5)? I propose later.
5. Is the first-night shelter (brain silent, §5.4) the minimal built-in box or a cached last design?
6. Do you want a Claude review round after step 3 (proposal rule: before a large change)?
